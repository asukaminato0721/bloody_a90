# 截图、桌面画笔和语音工具

用户确定的范围包括 A90 配置、按键、宏和手势。
附带工具可调用 Linux 应用，不要求重做官方编辑器或语音程序。
当前使用手势的“打开文件或程序”动作调用工具。

## Linux 设置

1. 安装所需的截图、桌面画笔或语音应用。
2. 在手势页选择方向，再选择“打开文件或程序”。
3. 填写可执行程序的完整路径。
4. 按该程序的说明填写参数，每行一个。
5. 点击“替换当前方向的动作”。
6. 点击“应用全局设置”。需要导出时，再保存手势文件。

参数中的空格属于同一个参数。引号按原文传递，不用于组合参数。
空行表示空参数。末尾换行不增加参数。
例如，工具要求两个参数时，应把两个参数写在两行，而不是写成一条命令。
应用自行处理区域选择、笔迹清除和语音录制开关。
驱动在手势识别后启动程序一次，不模拟官方工具内部的按下和释放状态。
启动和进程回收不会阻塞鼠标输入。
尚未测试用户实际选择的截图、画笔或语音应用。

带参数的动作仍使用 `Simulator=20`、`Action=3`。
`MacroName` 保存目标，Linux 扩展字段 `LinuxArguments` 保存参数文本。
现有的无参数动作继续按原方式执行。
官方 `Simulator=16/17/29` 动作不自动转换。用户替换前，文件读写保留其原值。
启用检查会指出当前不支持的方向，避免在执行时静默丢弃动作。

## 原 EXE 证据

对象为 `BloodyWorkShop8.exe`，SHA-256：

```text
4a76f6ef4b6e7da699afbd8d3d780ae9747b599af795531a39e3eb5d93c93162
```

依据来自分发器 `0045cd4c`、反汇编、VCL 元数据和 Ghidra 反编译。
反编译中的 Delphi 参数位置需与汇编核对。
以下地址为此 EXE 的首选装载地址。

### Simulator 16：截图

`Object=1` 进入 `013dd9a8`。
阶段 1 且 `Action=0/1` 时传入 1，初始化并显示静态截图窗口。
阶段 2 且 `Action=0/2` 时传入 0。
窗口已显示时，后者调用 `013dca58` 完成选择并进入后续编辑状态。
该调用不能简单解释为隐藏窗口。
`Action=3` 在此分支没有调用。

窗口类为 `TFScreen`，VMT 为 `016065ec`。
发布的方法包括矩形、椭圆、箭头、画笔、文字、马赛克、撤销、保存和完成。
这些方法表明该对象包含编辑流程。

`Object=2` 进入 `013f10bc`。
`Action=0` 的阶段 1 传入 1，但该参数在目标函数中直接返回。
阶段 2 传入 0，显示截图模式菜单。
如果菜单已显示，`013fdb70` 将其置前，并移到当前指针位置。
不能把这条路径解释为关闭菜单。
窗口类为 `TcaptureScreenShotModeSelect`，VMT 为 `0160f9b8`。
其方法包含静态截图、自动滚动截图和滚动截图的选择入口。

### Simulator 17：桌面画笔

`Action=0` 的阶段 1 调用 `0045def4`，准备窗口并开始记录笔迹。
阶段 2 调用 `0045ef58`，结束当前笔迹。
若清除条件成立，还会调用 `0045f10c`。
后者注册并发送消息 `AM_硃砂筆_筆跡清除`。
该文字和笔迹数据结构共同确认功能为桌面画笔。

### Simulator 29：语音程序桥接

`Action=0` 的阶段 1 和阶段 2 分别发送消息 `800d` 和 `800e`。
目标是驱动窗口对象 `01610150` 对应的 HWND。
当前证据不能把它写为直接向语音进程发送消息。

同一对象的 `007bd968` 查找窗口类 `BloodySpeechRecognizerApp`。
该函数还引用 `Tools\BloodySpeechRecognizer.exe`，并包含启动和再次查找窗口的路径。
这确认了外部语音工具的关联，但尚未完整跟踪两条消息的转发处理。
Linux 工具调用不依赖这些 Windows 消息。

## 检查

`tests/host_tool.rs` 覆盖 XML 保存与载入、主机 VM 和后台启动线程。
测试子进程记录实际收到的参数字节。
检查包含中文、表情符号、空格、空参数、引号和命令替换文字。
边界检查拒绝控制字符、过长参数和非可执行目标。
隔离 evdev 测试还覆盖实际手势触发、参数传递和启动失败后的普通输入转发。
这些检查不启动真实截图、画笔或语音应用。
